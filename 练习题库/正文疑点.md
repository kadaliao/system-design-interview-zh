# 出题与审校中发现的正文疑点

为 iOS App 编写和审校题库时，逐章对照正文发现的问题。**正文尚未修改**，这里只记录，供后续决定是否加批注或更正。题库遇到这些地方时已经绕开，或在题干里写明了假设。标“推断”的条目没有对照原书核实。

## 数字与估算

| 章 | 位置 | 问题 |
|---|---|---|
| 2 | 可用性列表 | 六个 9 的 31.56 秒按一年 365.25 天算，其余各行按 365 天（应约 31.54 秒），口径不一。 |
| 2 | 机器数小例子 | “按 30% 余量取 26～30 个”混用了“机器多加 30%”（26 台）和“目标利用率 70%”（约 29 台）两种算法，而 Q02-04 要求区分。 |
| 2 | 延迟表 | 标注“2020 年参考”，数值却是约 2010 年的经典版本（如 SSD 随机读 150 µs）。（推断） |
| 3 | 时间分配 | 四步建议时长合计 26～55 分钟，与“45 分钟面试”对不上，只能当弹性区间。 |
| 4 | 固定窗口批注 | 12:00:59 与 12:01:00 各 100 次说成“约 1 秒内”，严格说最长近 2 秒；Q04-03 用 59.9 与 00.1 秒（约 0.2 秒）更严谨。 |
| 8 | 截取前 7 位批注 | “取至少 42 位哈希换算成 Base62 再截取 7 位”：2^42 约 4.4 万亿大于 62^7，换算后是 8 位，应说明取低 7 位（对 62^7 取模）。 |
| 13 | 估算 | 48,000 QPS 没有推导，批注只说明是设计假设。 |
| 14 | 存储估算 | 150 TB 按原片大小推算，没说明不含转码版本和副本。 |
| 17 | 估算 | 33.4 万 × 40 ≈ 1,336 万，原文写约 1,400 万，由此推出的 140 台也偏多。 |
| 18 | 粗略估算 | 20 万 QPS 需要假设“每 15 秒上传一批”才推得出，正文没写；70 PB 也只有结果。 |
| 19 | 数据存储 | “HDD 每秒数 MB”比常见的每秒上百 MB 低约两个量级（英文原笔记即如此）。（推断原书为数百 MB） |
| 22 | 估算取整 | `1,000,000 × 0.7 / 3` 约 23.3 万，正文写 ≈ 24 万；`240,000 / 10^5` 为 2.4，正文写 ≈ 3 TPS，都向上取整但没交代。 |
| 22 | 转化漏斗 | “三步、每步 10%”容易读成三次转化（得 3,000），实际是三个页面、两次转化（300→30→3）。 |
| 22 | 分片示例 | “QPS 增加 1,000 倍”后举 30,000 QPS 分 16 片，但 3 TPS × 1,000 = 3,000，30,000 只对得上“预订页 30 QPS × 1,000”，建议注明是另设例子。 |
| 23 | 估算 | 每人每天发 10 封、收 40 封，收发不对称的来源（外部来信、群发）没解释。 |
| 28 | 需求与估算 | 访谈写“每天数十亿订单”，估算用“每天 10 亿订单”。 |
| 29 | P28-03 | 5 秒预算中“追日志与重建”只分到 2 秒，例子却说“追赶 5 秒已花完整个预算”，说法偏保守。 |

## 前后不一致或表述不清

| 章 | 位置 | 问题 |
|---|---|---|
| 1 | 缓存 | “先更新数据库再删缓存”只提删除失败，没提并发读未命中回填旧值的竞态窗口（补充建议）。 |
| 3 | 估算译名 | “纸巾盒背面估算”与第 2 章“数量级估算”不一致，常见译法是“信封背面”。 |
| 5 | 实际应用 | 列表写 Amazon DynamoDB，紧接的批注谈的是 2007 年 Dynamo 论文，两者不是同一个系统，哈希环模型出自后者。 |
| 5 | 优点 | 直接写“缓解热点”，而前文批注已指出“数据均匀不等于访问均匀”，应限定为 key 分布不均造成的热点。 |
| 6 | 最终架构 | 只说协调节点是代理，没说明任意节点都可担当协调者，“去中心化”的程度要靠读者推断。 |
| 7 | 标题层级 | “### 批注：为什么组合后不重复”是三级标题，后面 Snowflake 的“优点”、准确性批注和“算一次容量”在锚点上都挂到这条批注下。 |
| 8 | API | `GET api/v1/shortUrl` 没标出短码是路径变量，原书一般写作 `api/v1/{shortUrl}`。 |
| 8 | 缩短流程 | 第 1 步“先查 longURL 是否存在，存在就复用”写成唯一流程，批注又说复用与否是产品策略；也隐含要给长网址建索引。 |
| 8 | 数据模型 | 没说唯一索引建在哪一列，而面试模板和批注都依赖“数据库唯一索引兜底”。 |
| 9 | BFS | 漏了原书指出的另一个问题：同一页面的链接大多指回同一主机，并行 BFS 会压垮站点（礼貌队列的理由）。（推断） |
| 9 | 工作流程 | 没写“存入 Content Storage”；“峰值 800 QPS”与“页/秒”混用；一致性哈希被归在“健壮性”下。 |
| 10 | 退订 | 需求写“关闭指定类型的通知”，其他组件写“各渠道的 opt-in/opt-out”，粒度不一；最终 5 步流程缺“发送前检查退订与限流”。 |
| 11 | 扇出 | “排除静音、屏蔽……的好友”没说清是谁静音了谁。 |
| 12 | 消息流程 | 一对一流程省掉了原书的消息同步队列；同步条件用 `recipient_id`，而群聊表只有 `channel_id`。 |
| 13 | 标题与归类 | “核心特性（Key Features）”出现两次；shard map manager 放在“负载分配”下，其实属于分片路由。 |
| 15 | 加密与去重 | 块服务器先加密再按哈希去重，若每块加密结果随机就认不出相同的块，正文只在批注里带过。 |
| 16 | Geohash | 写成“分四象限再细分”，实际是经度、纬度交替二分，每个字符编码 5 位；S2 归为“树类”是沿用原书分法。 |
| 17 | 订阅时机 | 初始化时“订阅好友的频道”，API 一节又说“好友首次上线时订阅”，离线好友的频道要不要订阅没说清。 |
| 17 | 历史库 | 周期更新流程里同步写历史库，面试模板却说“历史库异步留档”。 |
| 18 | 标题 | “地图渲染”出现两次，深入内容在第二处。 |
| 19 | ISR 示例 | 说副本 2、3 “跟上”了，那两条消息却仍未提交，“跟上”应指落后在阈值内。 |
| 19 | 消费者流程 | 把“组协调器不是 ZooKeeper”列为第 3 步，它是说明而不是步骤。 |
| 20 | 告警渠道 | 范围写“邮件、电话、PagerDuty、Webhook”，告警系统一节写“邮件、短信……”（英文原笔记即如此）。 |
| 21 | 对账 | 按 Kappa 思路重算，但每日对账是另一条批处理路径；若不复用同一套聚合逻辑，实际是 Lambda 式两套代码。（推断） |
| 22 | CHECK 约束 | `CHECK((\`total_inventory - total_reserved\` >= 0))` 的反引号包住整个表达式，MySQL 会当成列名，语法不通。 |
| 23 | 发信流程 | “保存到已发送”排在投递之后，与常见实现（入队时即写已发送）不同。 |
| 26 | 数据模型 | `payment_orders` 表是 `buyer_account`，API 的 `payment_order` 是 `seller_account`；注释说“收款流程不需要 `seller_info`”，而第 6 步要更新卖家钱包。 |
| 26 | 重试 | 把指数退避写成“后一次间隔为前一次两倍”，2 倍只是常见取值。 |
| 27 | 推送对象 | 前文说只读状态机推送给反向代理，最终生命周期第 5 步写推送给协调者。 |
| 27 | TC/C 顺序 | 对比表说 TC/C “执行顺序可任意安排”，故障一节要求先扣后加；实指 Try 阶段只动转出方，建议加批注。 |
| 27 | 图片 | 文件名拼错：`wallet-service-state-macghine.png`（不影响显示）。 |
| 28 | API 类型 | “查询成交”请求的 `orderId` 是 String，响应和创建订单返回的 id 是 Long。 |
